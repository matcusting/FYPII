# UTS Housing & Roommate Finder

A local development build of the student housing project. The React website and Express/PostgreSQL API cover accounts, student and landlord verification, property authorization, moderated property listings, search and favorites, roommate matching, inquiries and consent-based messaging, rental-proof reviews, reports, notifications, and administration. The website keeps its existing visual style. English is the default interface language; users can switch to Bahasa Melayu or Simplified Chinese. The seeded accounts and property are fictional.

## Open the complete site locally on Windows

Use this workflow when you need the administrator to download the same student or landlord documents that an applicant uploaded. Install Node.js 24 and Docker Desktop, start Docker Desktop, then download and extract the [whole `codex/brevo-email-setup` branch](https://github.com/matcusting/FYPII/archive/refs/heads/codex/brevo-email-setup.zip). In the extracted project folder, double-click **`START-REAL-SITE.cmd`**. It prepares PostgreSQL, a loopback-only ClamAV document scanner, the real API and email worker, the React frontend, and a private local administrator with a randomly generated password shown once in the launcher window. Open **http://localhost:5173** in Chrome and keep the service windows open. The launcher uses its own folder, so it does not depend on PowerShell starting in `C:\Windows\System32`.

Follow [WINDOWS_LOCAL_SETUP.md](WINDOWS_LOCAL_SETUP.md) for the first-run steps, the local email outbox, a fictional student and landlord upload exercise, and troubleshooting. The default launcher does not add accounts with publicly documented demo passwords. Stop the API, worker and frontend windows with Ctrl+C; `docker compose down` stops PostgreSQL and the Compose-managed scanner without deleting their volumes. The database and private evidence files remain on this computer. This is local development, not an internet deployment.

The separate [`FYPII-Windows-Chrome-preview.zip`](preview-downloads/FYPII-Windows-Chrome-preview.zip) opens at `http://127.0.0.1:4173/` and only simulates the workflow: it discards uploaded files and gives administrators placeholder downloads. It cannot be used to inspect an actual student ID, offer letter, landlord identity document or rental authorization. Use only fictional test documents in either local workflow until email delivery, private-file backups, access policy and retention have been arranged.

The language selector is available in the site navigation and role dashboards. It remembers the choice in this browser. Chat messages and user-entered listing text stay in their original language. If you switch accounts in another browser tab, the message composer resets its draft; reload any older tab before sending a reply. The API checks that the sender shown by the browser is still the signed-in account.

Student account settings collect a private phone number alongside the student's name, email, university and bio. The university shown in the profile does not determine verification: the API uses the verified school email's campus domain. Housing budget, preferred move-in date, and preferred area are edited in **My Lifestyle Profile** instead. The dashboard's **Find a Roommate** action opens that profile directly; university is never shown to roommate matches.

In **My Lifestyle Profile**, a student may select male, female, or **Prefer not to disclose**. This is self-reported and stays private unless the student separately enables **Show my gender to matches**. Landlords can mark each listing **All genders welcome**, **Men only**, or **Women only**; the choice is displayed on the listing and can be used as a search filter. A student's roommate-profile choice does not automatically filter housing results or prevent an inquiry.

## Student verification

A new student account must use an email address whose **exact domain** appears on an active campus in the admin settings. The fictional UTS campus seed includes `student.uts.edu.my` for testing the domain rule. After registration, the student enters the six-character email verification code, signs in, then submits **both** a student ID photo (JPG/PNG) and an offer letter (PDF/JPG/PNG) from Profile Settings. Each file may be up to 5 MB. Expired or missing codes can be requested again from Verify Email, subject to a cooldown. An administrator reviews the two private files, confirms that the card's Student ID matches the school email prefix, and manually enters the study-end date supported by the offer letter before approving. Verified-student access expires after that study-end date, and the student must submit current proof for another review. The original evidence is separately eligible for cleanup one calendar year after the recorded end date; the date is not inferred from OCR or filenames. The review form separately records an authorized school enrollment check, if one was actually performed; no UTS integration is claimed without school authorization. School-email ownership alone does not grant verified-student access. A rejected applicant can submit a new request.

The seeded `student@demo.local` and `candidate@demo.local` accounts are already marked verified for local feature testing; they do not test this new application flow. The local email worker writes verification codes to `uts-housing-api/data/outbox` when SMTP is absent. Use fictional files for local tests, and never add real student IDs or offer letters to Git, the demo seed, or a preview ZIP. Production use needs working SMTP and private-file storage with suitable access controls and retention rules.

## Landlord verification and listing authorization

For the identity, company, title and rental-authority checks in Sarawak, see the [Chinese landlord review guide](LANDLORD_REVIEW_SOP.zh-CN.md). The [law-firm handoff checklist](LAW_FIRM_REVIEW_HANDOFF.zh-CN.md) explains the engagement, limited access and privacy decisions needed before sending real documents to an external reviewer. A business card by itself does not establish that a firm has accepted the appointment.

A landlord registers with a name, personal or business email, phone number, and password, then verifies ownership of that email through the emailed link. Students and landlords may request a six-digit phone code from Profile Settings. A local outbox code tests the workflow without verifying phone ownership; real SMS verification requires a configured Twilio account and successful code entry. The landlord can prepare draft listings while verification is pending.

Before a landlord listing can be published, two separate applications must be reviewed: the landlord's identity (individual identity document, or company registration and representative authority documents) and evidence of the right to rent out **that specific property**. A property owner, agent, or subletter chooses the corresponding authorization path and supplies the required proof. Verified students who sublet must also submit property authorization. The administrator assigns each new identity and property-authorization case to a restricted legal reviewer, who can inspect only assigned evidence and recommend a decision. Final approval requires the lawyer's affirmative, recorded recommendation and an administrator's separate decision. The admin also reviews the listing content and photos before publication. Property authorization is tied to the listing and its complete address; changing the address or authorization evidence requires another review. An email-verified account or approved identity alone does not grant publication rights.

Applying the new database migration pauses previously published listings because they have not passed these new checks. Their owners must submit evidence and ask for a fresh listing review. The fictional sample listing created by the local seed has its own explicit synthetic review records so the demonstration remains browsable.

Identity and authorization documents are submitted privately by applicants and can be downloaded only by the assigned restricted legal reviewer and authorized administrators; applicants can see their review status and reason. The documents are never shown in public listings. A review badge means evidence was assessed and a website decision was made; it is not a guarantee that a property or document is authentic. The operator-selected document retention is one calendar year after the offer-letter study-end date for approved student files, and two calendar years after approval expiry, rejection or revocation for landlord identity and property-authorization files. A [dry-run-first retention command](uts-housing-api/RETENTION_OPERATIONS.md) implements this policy; it is not scheduled or applied automatically. Use only fictional documents in local tests and the preview. Before processing real identity documents, set up secure private storage, real email delivery, a reviewed legal notice, off-device backups and a process for disputed authorization. No environment is deployed by these repository changes.

Landlord identity approvals expire after at most 365 days and property authorizations after at most 180 days by default; both limits are configurable, and reviewers can select an earlier date. Administrators can revoke an active approval with a reason. An expired or revoked approval immediately removes affected properties from public search, photos, favorites and inquiry/review access. The email worker also pauses affected published listings and notifies owners. Renewal requires new proof and another review. The administrator portal now includes account deletion requests and an audit-log view.

## Property addresses and location privacy

Listing owners enter a full street address when creating or editing a property. In local development the server sends that address to the public Nominatim address-lookup service at no more than one request per second; a configured `GEOCODER_URL` can be used instead. The server stores the returned coordinates privately and calculates the approximate straight-line distance to the listing's selected campus. Students can see that distance, filter by a maximum distance, and sort nearest first. They can also show only homes whose owners confirmed availability within the last 30 days; this is an owner statement, not an independent live occupancy feed. A failed or imprecise lookup leaves the distance unavailable; it does not block a draft. Existing listings without coordinates are retried by `npm run locations:backfill`, which the Windows launcher runs after migrations. Owners can also select **Retry Address Lookup** in Manage Properties after a failed lookup; the API limits retries for the same address to once per minute. Campus coordinates are managed by administrators and should be checked against the real campus entrance. This is not driving or walking distance. Owners choose whether an approved listing shares its full address with signed-in students; otherwise only the approximate area and calculated distance are public. The site has no embedded map or coordinate entry, and exact coordinates are never returned in listing responses. Configure a suitable address provider before hosting the site.

## Checks and project files

Run `npm run typecheck`, `npm test`, and `npm run build` in both `uts-housing-api` and `uts-housing-frontend`. Run `npm run lint` in the frontend. API integration tests can use a migrated disposable PostgreSQL database via `TEST_DATABASE_URL`. CI performs these checks and applies the committed SQL migration to its test database. The frontend also has `npm run test:browser` for a running local site and a [manual QA checklist](uts-housing-frontend/QA_CHECKLIST.md). The API [private-media guide](uts-housing-api/PRIVATE_MEDIA_OPERATIONS.md) explains integrity checks and safe orphan quarantine.

The [API guide](uts-housing-api/README.md) explains migration, seed, and email behavior. [Frontend guide](uts-housing-frontend/README.md) describes its routes. The [Render deployment guide](deploy/RENDER.md) covers the prepared production Blueprint, required secrets and outstanding external setup; **nothing has been deployed**. An encrypted local backup command, Windows scheduled-task installer, optional mirror and retention, and isolated restore rehearsal are documented in [Windows setup](WINDOWS_LOCAL_SETUP.md). A production off-device backup destination and recovery procedure must be established for Render's private disk before storing real documents. [Brevo is selected for email](deploy/BREVO.md), but its SMTP credentials and verified sender have not been configured or tested; the draft legal notice requires legal approval. Production startup refuses to run without HTTPS origins, SMTP, a real sender address and a persistent private-media path.
