# UTS Housing API (local development)

This Express API stores accounts, listings, roommate profiles, messages, reviews, and moderation records in PostgreSQL. The demo seed is **fictional** and is for local testing only. It must never be used as a real rental directory.

On Windows, use the repository's `START-REAL-SITE.cmd` and [complete local setup guide](../WINDOWS_LOCAL_SETUP.md). For a manual start, run `docker compose up -d postgres` from the repository root. In this directory, copy `.env.example` to `.env`, run `npm ci`, `npm run db:generate`, `npm run db:deploy`, `npm run db:init-local`, then `npm run dev`. The one-time initializer creates a local administrator with a random password printed once, plus the initial campus and facilities. Start `npm run email:worker` in another terminal. The frontend runs separately in `uts-housing-frontend` with `npm ci` and `npm run dev`; Vite forwards `/api` to port 3001. Open `http://localhost:5173` in Chrome. In development the API listens only on `127.0.0.1` by default.

To add fictional demo accounts and a published sample listing, explicitly run `npm run db:init-local -- --keep-demo-admin`, then set `CONFIRM_DEMO_SEED=1` and run `npm run db:seed`. In PowerShell, use `$env:CONFIRM_DEMO_SEED='1'; npm run db:seed`. The local-only accounts are `admin@demo.local`, `landlord@demo.local`, `student@demo.local`, and `candidate@demo.local`; their initial password is `Demo12345!` unless `SEED_DEMO_PASSWORD` is set. The normal initializer suspends an active public demo administrator if one already exists and does not reset its password; use the private local administrator for documents. The seed refuses `NODE_ENV=production` and non-local database hosts. The sample listing is explicitly labeled fictional and keeps its full address private by default.

Database changes are committed as SQL files in `prisma/migrations`. `npm run db:deploy` checks each migration's SHA-256 checksum and applies pending files in one PostgreSQL transaction under an advisory lock; it can be rerun safely. `npm run db:migrate` uses the same local migration executor. The Prisma Client still must be generated after changing `prisma/schema.prisma`.

The listing API requires a full address on creation. It returns that address only to the owner, administrators, and signed-in students when the owner chooses to share it after approval. Public visitors receive an approximate area. The frontend has no map or coordinate entry; legacy coordinates are never included in listing responses.

The account profile API lets students and landlords save a contact phone number. It appears only in their own authenticated profile response. Roommate matches do not disclose university, including for older profiles that previously opted in to sharing it.

Student registration requires an email address whose domain exactly matches one configured on an **active** campus. Admins can manage campus domains in the Campus Settings page; the fictional UTS seed includes `student.uts.edu.my`. This is a domain rule, not proof that an applicant is enrolled. The email verification link must first establish ownership of the school mailbox. Then `POST /api/v1/verifications` accepts multipart `method=DOCUMENTS`, `studentId` (JPG/PNG), `offerLetter` (PDF/JPG/PNG), and an optional note of up to 500 characters. Both files are required, and each is limited to 5 MB. The server checks file contents and MIME types, stores random-name files under `MEDIA_PRIVATE_DIR/verifications`, and creates a pending request. It determines the university from the campus domain rather than trusting profile text or an uploaded filename. The older email-only and single-proof submission methods are no longer accepted.

Only an authenticated administrator can open the two files through the verification detail's `studentIdUrl` and `offerLetterUrl`. Admin approval requires a still-verified school email, an active matching domain, both stored documents, and an explicit `studentIdMatchesEmail: true` reviewer attestation. The reviewer compares the card's Student ID with the part before `@` in the school email; there is no automatic OCR or enrollment lookup. Rejection records a reason, removes that submission's private files, and lets the applicant resubmit. Approval of an account-deletion request removes that user's verification records and private files. At most three verification submissions are allowed per student in 24 hours. Documents and user-specific identifiers must not be put in the demo seed, Git history, logs, or preview package. Before accepting real submissions, configure email delivery, secure private-file backups and retention, and review the privacy and access policy.

If an email verification link expires or is lost, `POST /api/v1/auth/resend-verification` accepts an email address and gives the same response whether or not an eligible account exists. Requests are limited per IP and to one new link per account every ten minutes. A replacement invalidates earlier unused links. The Verify Email page exposes this flow; local development still needs the email worker running to write a link to `data/outbox`.

Landlord registration requires a contact phone number as well as name, email and password. The normal email verification link proves control of the mailbox, but the phone number is only recorded, not SMS-verified. Landlord identity review and property authorization review are separate from student verification and from normal listing content moderation. An individual landlord supplies identity evidence; a company supplies company registration and representative authority evidence. A property owner, agent or subletter then supplies authorization evidence for each listing. Each authorization is bound to the complete property address, so changing the address or proof invalidates its approval. Landlords may save drafts while reviews are pending; a listing cannot be submitted or published without the required approvals. Older listings must be reviewed under the new rules instead of inheriting approval.

Identity and property approvals have reviewer-set expiry dates, capped by `LANDLORD_IDENTITY_VALID_DAYS` (default 365) and `PROPERTY_AUTHORIZATION_VALID_DAYS` (default 180). A blank reviewer date uses that maximum; choose an earlier date when the supporting document ends sooner. An approval expires at the end of the selected date in Malaysia time. Existing approvals without expiry dates become immediately expired when the lifecycle migration runs, so their documents must be reviewed again. An administrator can explicitly revoke an active identity or property approval with a reason. Revocation pauses affected listings and is sent to the owner. Expired approvals are excluded from public listing, photo, favorite, inquiry and review access immediately; the email worker also sweeps expired approvals every minute to pause affected listings and notify owners. Renew by submitting fresh documents for review; an old approval is never automatically restored.

The identity form posts multipart data to `POST /api/v1/landlord-verifications/identity`: `kind=INDIVIDUAL|COMPANY` and `identity` (JPG/PNG), plus `companyRegistration` and `representativeAuthority` (PDF/JPG/PNG) for a company. `GET /api/v1/landlord-verifications/me` returns the latest status and review reason. For each draft listing, `POST /api/v1/landlord-verifications/listings/:id` takes `kind=OWNER|AGENT|SUBLETTING`, `proof` (PDF/JPG/PNG), and `supporting` (PDF/JPG/PNG) for agents or subletters. `GET` on the same path returns the listing's current authorization status. Administrators use `GET` and `PATCH /api/v1/admin/landlord-verifications/:id` or `/api/v1/admin/property-authorizations/:id` to review, approve or reject; the queue endpoints are their collection paths. Each document is limited to 5 MB, and rejected applications can be resubmitted after review.

Keep landlord identity and rental-right documents in the configured private media directory, outside public listing-media URLs. Only authorized administrators should retrieve files to make a decision. Record rejection reasons and audit moderation decisions; delete unneeded files when a submission is rejected or an account is deleted. An admin decision records review of the supplied evidence, not a guarantee of legal ownership or document authenticity. Before handling real documents, configure protected storage and backups, administrator access controls, a retention schedule, and procedures for authorization expiry or revocation. No real identity files belong in the demo seed, tests, Git history or preview package. See [private media operations](PRIVATE_MEDIA_OPERATIONS.md) for a read-only integrity check and reversible orphan quarantine.

Run `npm run typecheck`, `npm test`, and `npm run build` for API checks. The email worker runs separately with `npm run email:worker`; configure SMTP values in `.env` to deliver queued messages. In local development without SMTP, the worker writes email messages to `data/outbox` so verification and reset links can be tested. API transactions do not wait for delivery. Production requires SMTP.

The administrator UI also exposes account-deletion requests (`/admin/deletion-requests`) and the read-only audit log (`/admin/audit-logs`). The API must still be connected to a real database to process them. Production startup requires HTTPS frontend origins and public base URL, SMTP and a real sender address, a strong session secret, and a persistent absolute `MEDIA_PRIVATE_DIR`. An optional official Help-page mailbox can be set as `VITE_SUPPORT_EMAIL` in the frontend build; do not put any secret in a `VITE_` value.

On Windows, install Node.js 24 and Docker Desktop first. In PowerShell, use `Copy-Item .env.example .env` inside this directory before starting the API. Run the API, email worker, and frontend in separate PowerShell windows. The API is available only on your computer until you choose to deploy it.
