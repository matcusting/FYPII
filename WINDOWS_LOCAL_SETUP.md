# Run the complete site on a Windows computer

This is the **real local application**, with PostgreSQL, the Express API, a private file directory, the email worker and the React frontend. It opens at **http://localhost:5173/**. The separate Windows preview ZIP opens at `http://127.0.0.1:4173/`; that preview discards uploaded files and cannot be used to review an actual upload. Neither option deploys a website to the internet.

## First start

1. Install [Node.js 24](https://nodejs.org/) and [Docker Desktop](https://www.docker.com/products/docker-desktop/). Start Docker Desktop and wait until it reports that the engine is running. If you install either program while a terminal is open, close that terminal and open it again.
2. Download the **whole** `codex/brevo-email-setup` branch of [matcusting/FYPII](https://github.com/matcusting/FYPII/tree/codex/brevo-email-setup) and extract it, or clone it with Git. Open the extracted `FYPII` folder in File Explorer. Do not use `FYPII-Windows-Chrome-preview.zip` for this workflow.
3. Double-click **`START-REAL-SITE.cmd`** in that folder. The launcher locates the project using its own location, so it works even if PowerShell previously opened in `C:\Windows\System32`. On the first run it installs locked npm dependencies, creates `uts-housing-api\.env` if missing, starts PostgreSQL and a loopback-only ClamAV scanner, applies database migrations, creates a private local administrator and sets up a sample campus/facility catalog. It preserves an existing `.env` except that it replaces the known example session secret with a random one; it does not clear the database. For this launch only, it also forces `MALWARE_SCAN_MODE=clamav` and `CLAMAV_HOST=127.0.0.1` in the child processes, so an older preserved `.env` cannot bypass scanning. **Save the randomly generated administrator password shown once in the launcher window.** Do not share it or include it in a screenshot.
4. Leave the three new windows titled **API**, **Email worker** and **Frontend** open. When the launcher reports that the site is ready, open **http://localhost:5173/** in Chrome. The launcher also tries to open Chrome automatically.

The first run downloads PostgreSQL and ClamAV Docker images, updates ClamAV virus signatures, and installs npm packages, so it can take several minutes. ClamAV publishes only on your computer's `127.0.0.1:3310`; the launcher waits for a successful scanner PING before opening the site. If a standalone container named `uts-housing-clamav` already exists with that loopback-only port mapping, the launcher reuses it instead of trying to bind another scanner to the same port. If the launcher reports that `docker.exe` or `node.exe` is missing, install the named program and reopen the launcher. If Docker is installed but not running, start Docker Desktop. Do not paste the startup commands into `C:\Windows\System32`.

## Update an extracted ZIP

Stop the API, Email worker and Frontend windows first. Keep your existing extracted FYPII folder: its ignored `uts-housing-api\.env` and `uts-housing-api\data` contain local settings and private uploads, while Docker's volume contains your database. Download the newer branch ZIP, extract it separately, then copy the files **inside** its FYPII project folder into your existing FYPII project folder and choose to replace files with the same names. Do not delete the old project folder or run `docker compose down -v`. Start Docker Desktop and run `START-REAL-SITE.cmd` from that same existing folder; it applies only the new migration and keeps existing accounts. Keep a separate backup of the database and private files before using important data.

The private administrator signs in as `local-admin@demo.local` with that one-time password. The normal launcher does **not** create accounts with public demo passwords. If an older local database still contains the publicly documented `admin@demo.local`, local initialization suspends it and revokes its sessions. If you lose the private password, use **Forgot Password** for `local-admin@demo.local` and open its local outbox message as described below. In local development, `.local` recipients always go to the private local outbox, even when Brevo SMTP is configured for real addresses. Brevo cannot deliver to this `.local` address; the reset link expires after one hour and must stay private.

You can also start from PowerShell with `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Start-LocalSite.ps1` while inside the extracted project folder. Only if you explicitly want the public fictional seed accounts and sample property, append `-SeedDemo`. That optional mode permits `admin@demo.local` and other sample accounts with `Demo12345!` in a fresh local database; never use it to review personal documents. The ordinary launcher does not enable it, and a previously suspended demo administrator is not reactivated.

## Test a real local document upload

Use fictional test images made in Paint, not real student cards, offer letters, identity cards, property titles or leases. For a student test, make one JPG/PNG labelled `Student ID — TEST ONLY` with a fictional ID such as `demo-test001`, and a second JPG/PNG labelled `Offer Letter — TEST ONLY`. Each must be under 5 MB. The offer letter can instead be a PDF. Keep these sample files on your own computer; they do not belong in Git.

1. At `http://localhost:5173/register`, register a student with a **new fictional** address such as `demo-test001@student.uts.edu.my`. The initial local campus permits the exact `student.uts.edu.my` domain. This is a local test address, not a real school mailbox.
2. The local email worker writes a verification message to `FYPII\uts-housing-api\data\outbox` when SMTP is not configured, or when a synthetic recipient ends in `.local`. Open that folder in File Explorer, sort by modified date, open the newest `.txt` file, and check its `To:` line. Open the `http://localhost:5173/verify-email?email=...` link and enter the six-character code from the same message. If the newest message belongs to another test account, find the one with the matching `To:` address. A local outbox code proves nothing about ownership of a real university mailbox; it only lets you exercise the local workflow. Older 64-character verification links remain usable until they expire.
   Brevo is the selected real mail provider. When your Brevo SMTP login, SMTP key and verified sender are ready, follow the [Brevo setup guide](deploy/BREVO.md) and put the settings in your private `uts-housing-api\.env` file. Run `npm run email:check -- --to=your-own-address@example.com` from that folder and check your inbox. This can be done while the website still runs locally; no deployment is required. Until then, leave `SMTP_HOST` blank to keep local outbox mode.
3. Sign in as the new student. Open **Profile Settings → Student Verification** at `http://localhost:5173/profile`, choose both fictional files and submit. The status changes to pending review.
4. Sign out, then sign in as `local-admin@demo.local` using the password saved during first start. Open **Student Verifications** at `http://localhost:5173/admin/verifications`, expand that request and click **Download Student ID** and **Download Offer Letter**. In this complete local application the downloaded bytes are the files you submitted, not preview placeholders. For approval, an administrator must manually compare the fictional ID with the part of the test email before `@`, check the confirmation box, and enter the study-end date supported by the fictional offer letter. The retention deadline is one calendar year after that date.

For optional phone-code testing, use **Profile Settings → Phone Verification**. Without a Twilio account, the code is written to `uts-housing-api\data\sms-outbox`; completing it tests the local workflow but does not verify phone ownership. See [SMS setup](uts-housing-api/SMS_SETUP.md) for real-delivery configuration. For a landlord test, register a new fictional `@demo.local` address and provide a test phone number. Verify its email using the local outbox, then open **Profile Settings → Landlord Identity Verification** to submit a fictional ID image. The administrator assigns this pending case at `/admin/lawyer-cases`; the fictional restricted reviewer opens `/lawyer/cases`, downloads the submitted file and records a recommendation. The administrator then reviews it at `/admin/landlord-verifications` and makes the final decision. After approval, the landlord creates a draft listing with a full address and photo, submits fictional evidence of the right to rent that specific property, and the administrator assigns that second case for legal review before deciding at `/admin/property-authorizations`. The files downloaded from the real API are the original local files, not `DEMO ONLY` images.

For actual landlord applications, follow the [Chinese landlord review guide](LANDLORD_REVIEW_SOP.zh-CN.md) to compare identity, current registry records and the right to rent each specific property before making either approval.

## Restricted legal-review workflow

Before creating a real reviewer account, independently confirm the firm's identity and written engagement, and agree on access, confidentiality, case transfer and retention using the [law-firm handoff checklist](LAW_FIRM_REVIEW_HANDOFF.zh-CN.md). Do not assume that an address printed on a business card is an authorized account address. For a **fictional local test**, open PowerShell in `uts-housing-api` and run `npm run lawyer:provision -- --name="Synthetic Legal Reviewer" --email="reviewer-test@example.test"`. This local-only command creates a dedicated LAWYER account and prints a random password once. Save it privately; it is never emailed and must not be committed or photographed. Do not reuse an administrator, student or landlord account for a reviewer.

An administrator opens `/admin/lawyer-cases` to assign each pending landlord identity or property-authorization case. The assigned reviewer signs in on the same local computer and opens `/lawyer/cases` to inspect only assigned files and submit a written recommendation. The administrator then reads the recommendation and makes the final website decision in `/admin/landlord-verifications` or `/admin/property-authorizations`. A new landlord approval cannot be granted without an affirmative recommendation and the required independent checks. Reassigning a pending case clears its previous recommendation. This workflow does not automatically contact the law firm or send applicant documents anywhere. Because this local site binds to your own computer, the firm cannot remotely open `localhost:5173`; use only fictional cases until a reviewed secure access arrangement exists.

## Evidence retention

The project owner has chosen these document-file rules: approved student ID and offer-letter files become eligible for cleanup one calendar year after the study-end date checked from the offer letter; landlord identity and property-authorization files become eligible two calendar years after approval expiry, rejection or revocation. Older student approvals without a recorded study-end date are skipped for manual review. The [retention operations guide](uts-housing-api/RETENTION_OPERATIONS.md) provides a read-only dry-run, an explicit apply command, a Windows wrapper and crash recovery. No deletion schedule is enabled automatically. From the project root, a dry-run is `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Run-EvidenceRetention.ps1 -StudentOfferEnd -IdentityYears 2 -PropertyYears 2`. Before an apply run, stop the local website services, make and verify an encrypted off-device backup, inspect the dry-run, and confirm that no legal hold applies. Pending cases and current landlord/property approvals are excluded. Encrypted backup copies have their own retention policy.

The API saves evidence under `FYPII\uts-housing-api\data\private`, which is ignored by Git. Student evidence download is restricted to authorized administrators; landlord identity and property-authorization evidence can also be downloaded by the active restricted reviewer assigned to that pending case. PostgreSQL uses a Docker volume. Closing the three service windows or running `docker compose down` does **not** erase the database or private files; do not run `docker compose down -v` unless you intentionally want to delete the database volume. Back up both the database and private directory before using important data. This local configuration is for development and does not send real emails or establish genuine student identity. If you later configure SMTP and choose to process real materials locally, protect that computer and its backups; the files remain on that computer and are not uploaded to GitHub.

To create an encrypted local backup, stop the API, email worker and frontend windows but leave Docker Desktop/PostgreSQL running. From the project folder run `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Backup-LocalSite.ps1 -Action create -File "D:\UTS-Backups\housing-2026-10-29.uthbak"`, changing the destination to a folder outside the project. The script asks twice for a private passphrase of at least 16 characters; losing it makes the backup unreadable. It saves a PostgreSQL dump, the local configuration, and private/legacy upload folders inside one AES-256-GCM encrypted file. Run the same command with `-Action verify` to check the archive, or `-Action rehearse` to restore it into a **temporary, isolated** database and check private-file references. Rehearsal deletes only that temporary database. Keep the passphrase separately from the backup. The tool never replaces your live database.

To schedule backups on **your Windows computer**, choose an existing external-drive or protected network-share folder accessible to your signed-in account. Stop the site and, from its project folder, run `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Install-BackupSchedule.ps1 -DestinationDirectory "E:\UTS-Backups" -DailyAt "02:00"`. On first installation, the installer asks for a passphrase twice, protects a scheduler copy with Windows DPAPI under your account, and registers a daily Windows task. Add `-MirrorDirectory "\\server\protected-share\UTS-Backups"` for a second copy; the task compares SHA-256 hashes before reporting success. Add `-RetainDays 30 -MinimumCopies 7` to remove only old scheduled archives after a successful new backup; without `-RetainDays`, nothing is deleted automatically. Each run verifies its encrypted archive, and once a week restores into a disposable database to check that the backup can actually be used. The log is `%LOCALAPPDATA%\UTSHousingBackup\backup.log`; check it and the Windows Task Scheduler history after the first run. To test immediately after closing the site, run `Start-ScheduledTask -TaskName 'UTS Housing Encrypted Local Backup'` in PowerShell, then inspect the log and destination folder. The task runs as the **same signed-in Windows user**, so that user must be logged in at the scheduled time or when Windows runs a missed task. Leave Docker Desktop running; the task starts PostgreSQL if needed, but aborts when the API is open to avoid an inconsistent database/file copy. A local drive or second partition is not an off-device backup: use a removable drive kept separately or an authorized protected network share for that. Keep the memorized passphrase separately from every backup; the DPAPI copy only works for that Windows account. Register the task again if you move the project folder or change the destination. This local scheduling is not a deployed production backup service.

When a landlord saves a full property address, the local API sends it to the Nominatim address service to calculate an approximate straight-line distance to the selected campus. The launcher retries addresses from older listings on startup. Students can filter and sort by distance. An unmatched address shows no distance; the landlord can check the address and select **Retry Address Lookup** in Manage Properties, or correct the address in the listing form. The full address remains subject to the landlord's sharing choice, but the distance is public. This service needs an internet connection; no map is installed.

## Stop or troubleshoot

Press **Ctrl+C** in the API, Email worker and Frontend windows. From the project folder, `docker compose down` stops PostgreSQL and a Compose-managed ClamAV scanner while preserving their volumes. A separately created `uts-housing-clamav` container is not part of Compose; Docker Desktop manages its restart policy. On the next day, start Docker Desktop and double-click `START-REAL-SITE.cmd` again. The launcher reapplies only pending migrations and does not replace existing accounts or documents.

If `localhost:5173` refuses the connection, check that the **Frontend** window is still open; if the page loads but data does not, check the **API** window and visit `http://127.0.0.1:3001/health/ready`, which should report `ready`. If startup stops at ClamAV, inspect the scanner container logs in Docker Desktop and wait for its initial virus-signature update; do not switch to `test-bypass` for real identity documents. If the launcher reports a port conflict, close the older local server using that port before retrying. A page at `127.0.0.1:4173` is always the separate in-memory preview.

When running the API directly instead of through the launcher, set `MALWARE_SCAN_MODE=clamav`, `CLAMAV_HOST=127.0.0.1`, and `CLAMAV_PORT=3310` in the private `uts-housing-api\.env` file, and leave `CLAMAV_SOCKET` blank. The scanner must be running and ready before uploading documents. Do not share the `.env` file or include its email credentials in screenshots.
