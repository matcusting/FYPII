# Run the complete site on a Windows computer

This is the **real local application**, with PostgreSQL, the Express API, a private file directory, the email worker and the React frontend. It opens at **http://localhost:5173/**. The separate Windows preview ZIP opens at `http://127.0.0.1:4173/`; that preview discards uploaded files and cannot be used to review an actual upload. Neither option deploys a website to the internet.

## First start

1. Install [Node.js 24](https://nodejs.org/) and [Docker Desktop](https://www.docker.com/products/docker-desktop/). Start Docker Desktop and wait until it reports that the engine is running. If you install either program while a terminal is open, close that terminal and open it again.
2. Download the **whole** `codex/frontend-preview` branch of [matcusting/FYPII](https://github.com/matcusting/FYPII/tree/codex/frontend-preview) and extract it, or clone it with Git. Open the extracted `FYPII` folder in File Explorer. Do not use `FYPII-Windows-Chrome-preview.zip` for this workflow.
3. Double-click **`START-REAL-SITE.cmd`** in that folder. The launcher locates the project using its own location, so it works even if PowerShell previously opened in `C:\Windows\System32`. On the first run it installs locked npm dependencies, creates `uts-housing-api\.env` if missing, starts PostgreSQL, applies database migrations, creates a private local administrator and sets up a sample campus/facility catalog. It preserves an existing `.env` except that it replaces the known example session secret with a random one; it does not clear the database. **Save the randomly generated administrator password shown once in the launcher window.** Do not share it or include it in a screenshot.
4. Leave the three new windows titled **API**, **Email worker** and **Frontend** open. When the launcher reports that the site is ready, open **http://localhost:5173/** in Chrome. The launcher also tries to open Chrome automatically.

The first run downloads a PostgreSQL Docker image and npm packages, so it can take a few minutes. If the launcher reports that `docker.exe` or `node.exe` is missing, install the named program and reopen the launcher. If Docker is installed but not running, start Docker Desktop. Do not paste the startup commands into `C:\Windows\System32`.

## Update an extracted ZIP

Stop the API, Email worker and Frontend windows first. Keep your existing extracted FYPII folder: its ignored `uts-housing-api\.env` and `uts-housing-api\data` contain local settings and private uploads, while Docker's volume contains your database. Download the newer branch ZIP, extract it separately, then copy the files **inside** its FYPII project folder into your existing FYPII project folder and choose to replace files with the same names. Do not delete the old project folder or run `docker compose down -v`. Start Docker Desktop and run `START-REAL-SITE.cmd` from that same existing folder; it applies only the new migration and keeps existing accounts. Keep a separate backup of the database and private files before using important data.

The private administrator signs in as `local-admin@demo.local` with that one-time password. The normal launcher does **not** create accounts with public demo passwords. If an older local database still contains the publicly documented `admin@demo.local`, local initialization suspends it and revokes its sessions. If you lose the private password, use **Forgot Password** for `local-admin@demo.local` and open its local outbox message as described below. The site cannot send mail to this `.local` address.

You can also start from PowerShell with `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Start-LocalSite.ps1` while inside the extracted project folder. Only if you explicitly want the public fictional seed accounts and sample property, append `-SeedDemo`. That optional mode permits `admin@demo.local` and other sample accounts with `Demo12345!` in a fresh local database; never use it to review personal documents. The ordinary launcher does not enable it, and a previously suspended demo administrator is not reactivated.

## Test a real local document upload

Use fictional test images made in Paint, not real student cards, offer letters, identity cards, property titles or leases. For a student test, make one JPG/PNG labelled `Student ID — TEST ONLY` with a fictional ID such as `demo-test001`, and a second JPG/PNG labelled `Offer Letter — TEST ONLY`. Each must be under 5 MB. The offer letter can instead be a PDF. Keep these sample files on your own computer; they do not belong in Git.

1. At `http://localhost:5173/register`, register a student with a **new fictional** address such as `demo-test001@student.uts.edu.my`. The initial local campus permits the exact `student.uts.edu.my` domain. This is a local test address, not a real school mailbox.
2. The local email worker writes a verification message to `FYPII\uts-housing-api\data\outbox` when SMTP is not configured. Open that folder in File Explorer, sort by modified date, open the newest `.txt` file, and check its `To:` line. Open the `http://localhost:5173/verify-email?email=...` link and enter the six-character code from the same message. If the newest message belongs to another test account, find the one with the matching `To:` address. A local outbox code proves nothing about ownership of a real university mailbox; it only lets you exercise the local workflow. Older 64-character verification links remain usable until they expire.
3. Sign in as the new student. Open **Profile Settings → Student Verification** at `http://localhost:5173/profile`, choose both fictional files and submit. The status changes to pending review.
4. Sign out, then sign in as `local-admin@demo.local` using the password saved during first start. Open **Student Verifications** at `http://localhost:5173/admin/verifications`, expand that request and click **Download Student ID** and **Download Offer Letter**. In this complete local application the downloaded bytes are the files you submitted, not preview placeholders. For approval, an administrator must manually compare the fictional ID with the part of the test email before `@` and check the confirmation box.

For a landlord test, register a new fictional `@demo.local` address and provide a test phone number. Verify its email using the local outbox, then open **Profile Settings → Landlord Identity Verification** to submit a fictional ID image. The administrator reviews and downloads it from **Landlord Identity Review** at `/admin/landlord-verifications`. After approval, the landlord creates a draft listing with a full address and photo, submits fictional evidence of the right to rent that specific property, and the administrator reviews it at `/admin/property-authorizations`. Both original local files are downloaded from the real API, not replaced with `DEMO ONLY` images.

The API saves evidence under `FYPII\uts-housing-api\data\private`, which is ignored by Git. Only authorized administrators can use the private download endpoints. PostgreSQL uses a Docker volume. Closing the three service windows or running `docker compose down` does **not** erase the database or private files; do not run `docker compose down -v` unless you intentionally want to delete the database volume. Back up both the database and private directory before using important data. This local configuration is for development and does not send real emails or establish genuine student identity. If you later configure SMTP and choose to process real materials locally, protect that computer and its backups; the files remain on that computer and are not uploaded to GitHub.

## Stop or troubleshoot

Press **Ctrl+C** in the API, Email worker and Frontend windows. From the project folder, `docker compose down` stops PostgreSQL while preserving its volume. On the next day, start Docker Desktop and double-click `START-REAL-SITE.cmd` again. The launcher reapplies only pending migrations and does not replace existing accounts or documents.

If `localhost:5173` refuses the connection, check that the **Frontend** window is still open; if the page loads but data does not, check the **API** window and visit `http://127.0.0.1:3001/health/ready`, which should report `ready`. If the launcher reports a port conflict, close the older local server using that port before retrying. A page at `127.0.0.1:4173` is always the separate in-memory preview.
